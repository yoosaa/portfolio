# 3D ポートフォリオの反復改修

既存のインタラクティブなポートフォリオに対して、小さく検証可能な改修を行うための手順。

現在起動しているブランチと、実際に描画されている画面を正しい状態として扱う。記憶だけを頼りに、以前のコンセプトを再現しない。

## 1. 正しい実装と画面を確定する

編集を始める前に、次を行う。

1. リポジトリ、現在のブランチ、worktreeのパス、開発サーバーの起動コマンドを特定する。
2. `git status --short`を確認する。明示的に依頼されていない限り、ブランチの切り替え、別worktreeの作成、reset、既存変更の上書きを行わない。
3. ルートまたはエントリーポイントから、実際に使用されているシーンコンポーネントとCSSをたどる。依頼された状態に影響するファイルを正確に確認する。
4. 現在描画されている画面をキャプチャまたは確認する。「現在の雰囲気を維持する」という依頼なら、維持すべき色、レイアウト、タイポグラフィ、照明を具体的に整理する。

実装前に、次を簡潔に報告する。

- 対象のブランチとパス
- 編集するファイル
- 維持する見た目や挙動

## 2. 遷移を明示的な状態として管理する

インタラクティブなカメラ操作では、固定タイマーだけを状態遷移の根拠にしない。名前の付いた状態として管理する。

典型的な状態は次のとおり。

`room` → `zooming-to-display` → `projects` → `returning-to-room`

- カメラが目標位置へ到達してからProjects UIを表示する。到達判定には、カメラ位置、向き、FOVの許容差を定義する。
- 部屋へ戻るときは、最初にProjects UIを非表示にし、その後カメラを部屋の状態へ戻す。カメラの復帰完了後に、部屋の操作を再び有効にする。
- モニターをビューポート全体として見せる場合は、カメラの位置、look-at target、画角（FOV）を一緒にアニメーションさせる。
- 遷移中の割り込みは、意図的に設計した場合だけ許可する。それ以外の場合は、遷移中の連続クリックを無視する。
- カメラ座標だけを根拠に「対象がビューポート全体を満たしている」と判断しない。想定するビューポートサイズのブラウザで実際に確認する。

## 3. インタラクションの優先順位を明確にする

- 主役のオブジェクトには、主要なナビゲーションの役割を持たせる。
- 副次的なオブジェクトは、hover、光、わずかな動き、環境の変化などの小さな反応にとどめる。主役と競合するパネルを表示しない。
- 主要画面へ移動する導線と、部屋へ戻る導線には、意味のあるHTMLのbutton要素を用意する。`aria-hidden`が指定されたCanvas内のポインター操作を、唯一の導線にしない。
- `prefers-reduced-motion`を尊重する。長いカメラ移動の代わりに、短いフェードまたは即時の状態切り替えを用意する。

## 4. 依頼された範囲だけを変更する

カメラやインタラクションの調整を依頼された場合、無関係なテーマ、レイアウト、コンテンツ、プロジェクトデータを変更しない。

遷移を実現するためにUI変更が必要な場合は、互換性を維持できる最小限の変更にし、その変更が必要だったことを報告する。

テーマ変更を依頼された場合に限り、CSSとシーンコードの両方から古いテーマの色指定を検索する。その際は、次をまとめて確認する。

- Canvasの背景
- fog
- 照明
- マテリアル
- オーバーレイ
- ボタン
- 各コンテンツ画面

## 5. シーンの責務を守る

このリポジトリでは、シーンの見た目は宣言的なReact Three Fiberコンポーネントとして管理する。

- 静的な床・壁・階段は`RoomStructure.tsx`
- 家具・小物・ライト・クリック導線は`Room.tsx`と各家具コンポーネント
- カメラ遷移は`CameraRig.tsx`
- カメラの座標、注視点、FOVは`scene-config.ts`

`CameraRig.tsx`へ、色判定、`scene.traverse()`、オブジェクトの非表示、後付けgeometryなどの見た目補正を追加しない。見た目の変更は対象コンポーネントへ直接実装する。

シーン編集の具体的な座標系、窓、階段、家具、カメラ同期については、`src/features/landing/components/studio/SCENE_EDITING_GUIDE.md`を参照する。

## 6. 実際の体験を確認する

依存関係が利用できる場合は、プロジェクトに既存の検証コマンドを実行する。

最低限、次を実行する。

```bash
pnpm lint
pnpm build
git diff
```

その後、デスクトップ幅と、狭い画面幅またはモバイル幅のブラウザで、次の状態を確認する。

1. 初期状態の部屋ビュー
2. PC、モニターなど主役オブジェクトのhover、focus、クリック
3. ズームまたは遷移の途中
4. 遷移先のコンテンツビュー
5. 部屋へ戻った状態
6. 本棚、コルクボード、窓など副次導線の反応
7. 画面内の要素が各画面サイズでビューポート内に収まっているか

依存関係や実行環境の問題でアプリを起動できない場合は、編集した内容と確認できなかった項目を正確に説明する。その状態を「完了した」「動作している」とは報告しない。

## 7. 正確に報告する

最終報告には、次を含める。

- 変更したファイルと、それぞれの変更目的
- 実行した検証コマンドとその結果
- 実際にブラウザで確認した状態
- 残っている制約、または次に確認すべきこと

別ブランチ、切り離されたコピー、一時ディレクトリ、未確認のファイルに存在する変更について、「実装した」「保存した」「動作している」と報告しない。

commitやpushは、ユーザーが依頼した場合、またはリポジトリの作業手順として明示されている場合だけ行う。
